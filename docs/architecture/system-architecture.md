# System Architecture Diagram

![System Architecture Diagram](../../diagrams/system-architecture.png)

## Overview

The System Architecture Diagram provides a high-level representation of the AI Medical Assistant and illustrates the major components that make up the application.

The purpose of this diagram is to establish the structural foundation of the system before performing any security analysis. It identifies the core services, external dependencies, data stores, and monitoring capabilities involved in processing patient requests and generating AI-assisted medical guidance.

By understanding how these components are organized and how they interact, it becomes possible to systematically identify attack surfaces, trust relationships, and security-critical dependencies.

---

## Architectural Objective

The AI Medical Assistant is designed to help patients submit symptoms and medical questions, retrieve relevant medical references, and receive preliminary guidance generated by a Large Language Model (LLM).

The system combines traditional web application components with AI-specific services, including Retrieval-Augmented Generation (RAG), output guardrails, and integration with an external LLM provider.

---

## Architectural Layers

The architecture is divided into five logical layers.

### 1. User Layer

The User Layer contains the external actors who interact with the system.

- Patient
- Doctor

Patients submit symptoms and receive AI-generated responses. Doctors can review shared summaries through a secure dashboard.

---

### 2. Application Layer

The Application Layer contains the core web application services.

- Patient Web Interface
- Doctor Dashboard
- Authentication Service
- API Gateway

These components handle user interaction, authentication, session management, and request routing.

---

### 3. AI Processing Layer

The AI Processing Layer coordinates all model-related functionality.

- LLM Orchestrator
- Retrieval Engine
- Output Guardrails
- External LLM Provider

This layer retrieves supporting documents, constructs prompts, invokes the model, and validates generated responses.

---

### 4. Data Layer

The Data Layer stores structured and unstructured information.

- Patient Database
- Medical Knowledge Base

The Patient Database stores Personal Health Information (PHI), while the Medical Knowledge Base contains trusted clinical references used by the RAG pipeline.

---

### 5. Monitoring Layer

The Monitoring Layer provides operational visibility and security auditing.

- Logging and Monitoring

This component collects audit logs, application telemetry, and security-relevant events.

---

## Core Components

### Patient Web Interface

The front-end application used by patients to submit symptoms and view AI-generated medical guidance.

### Doctor Dashboard

A secure interface that allows authorized doctors to review summaries shared by patients.

### Authentication Service

Responsible for verifying user identities and enforcing access controls.

### API Gateway

Acts as the central entry point for all application requests.

### LLM Orchestrator

Coordinates prompt construction, retrieval, model invocation, and persistence.

### Retrieval Engine

Searches the Medical Knowledge Base and returns relevant documents.

### Output Guardrails

Validates model responses for privacy, safety, and policy compliance.

### External LLM Provider

A third-party model API used to generate responses.

### Patient Database

Stores patient records, summaries, and application data.

### Medical Knowledge Base

Contains trusted medical documentation used for Retrieval-Augmented Generation.

### Logging and Monitoring

Captures audit trails, security events, and operational metrics.

---

## High-Level Request Flow

A typical interaction follows this sequence:

1. A patient signs in and submits symptoms.
2. The request is authenticated and routed through the API Gateway.
3. The LLM Orchestrator retrieves relevant medical references.
4. A final prompt is constructed and sent to the external LLM provider.
5. The generated response is validated by Output Guardrails.
6. The response is stored and returned to the patient.
7. All relevant events are logged.
8. The patient may choose to share the generated summary with a doctor.

---

## External Dependencies

The architecture relies on an external LLM provider to perform inference.

This dependency introduces several security considerations:

- Sensitive prompt data may leave the organizational boundary.
- Third-party availability affects system reliability.
- Provider-side retention policies may impact privacy.
- Network communications must be encrypted.
